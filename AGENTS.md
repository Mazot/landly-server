# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Build
cargo build

# Run dev server (requires .env with DATABASE_URL, JWT_SECRET, JWT_EXPIRATION;
# REDIS_URL/S3_*/GOOGLE_* are optional). Always listens on 0.0.0.0:8080.
cargo run

# Run all tests
cargo test

# Run a single test by name
cargo test test_name

# Run tests with stdout
cargo test -- --nocapture

# Format code (required before committing)
cargo fmt

# Lint
cargo clippy

# Database migrations
diesel migration generate <name>
diesel migration run
diesel migration revert
```

On macOS with Homebrew `libpq` (keg-only), linking needs `PQ_LIB_DIR=/opt/homebrew/opt/libpq/lib` — Claude Code sessions get it from `.claude/settings.local.json`. Prefer it over `RUSTFLAGS="-L …"`: changing `RUSTFLAGS` invalidates every crate's fingerprint, so switching between a terminal and Claude rebuilds the world. Caveat: pq-sys 0.7.6 does not rerun its build script when `PQ_LIB_DIR` changes (its `rerun-if-env-changed` is mis-quoted), so after first setting it run `cargo clean -p pq-sys` once. The diesel CLI binary already links libpq by absolute path and needs nothing. The locked dependencies need Rust ≥ 1.94 (`aws-sdk-s3`); the crate uses edition 2024.

### Claude Code hooks (`.claude/settings.json`)

- **PreToolUse** `.claude/hooks/guard-edits.sh` denies Write/Edit on `src/data/schema.rs` and on any migration directory except the newest (new migration directories are allowed). Shell commands are not blocked — `diesel migration run` must still regenerate `schema.rs`.
- **PostToolUse** `.claude/hooks/rustfmt-edited.sh` runs `rustfmt` (edition 2024; 2021 under `scripts/crates`) on every edited `.rs` file; it never blocks, so a file that does not parse yet is left as is.
- Pre-approved commands: `cargo build/test/fmt/clippy`, `diesel migration *`, `docker compose ps/logs`.

## Architecture

This is an Actix Web REST API following a clean layered architecture. The main module is declared as a `[lib]` in `Cargo.toml`, so `src/main.rs` is the crate root.

### Layer order per request

```
HTTP → Authentication middleware → Controller → Usecase → Repository → Diesel/DB
                                                         ↓
                                             Cache (Redis or NoOp)
                                             Storage (S3/R2 or NoOp)
```

### Feature structure

Each domain feature lives under `src/app/features/<feature>/` with a consistent set of files:

- `config.rs` — registers Actix routes for the feature; wraps scope with cache middleware
- `controllers.rs` — Actix handler functions; extracts request data and delegates to usecase
- `requests.rs` — serde-deserializable input structs for query params / JSON bodies
- `usecases.rs` — business logic; accepts typed input structs, calls repository, calls presenter
- `repositories.rs` — Diesel queries; implements a `<Feature>Repository` trait
- `presenters.rs` — converts DB models to HTTP responses (`HttpResponse`)
- `entities.rs` — domain structs, feature enums and their Diesel models (distinct from the shared models in `src/data/models.rs`); domain types never live in `repositories.rs`
- `mod.rs` — module declarations + the feature's `#[derive(OpenApi)] pub struct ApiDoc`

The only deviations are `healthcheck` (controllers + `mod.rs` only) and `common`, which predates the split and keeps its request structs in `controllers.rs` and its models in `src/data/models.rs`.

Current features: `common`, `corridor`, `country_connection`, `healthcheck`, `images`, `moderation`, `organisation`, `person`, `report`, `review`, `saved`, `user`

### Adding a new feature — files to touch

Every new feature touches the same shared files: `src/app/features/mod.rs`, `src/utils/di.rs` (register the usecase in `DiContainer`), `src/main.rs` (`.configure(...)` + the feature's `ApiDoc` in `build_openapi()`), `src/app/drivers/middlewares/auth.rs` (`AUTH_REQUIRED_ROUTES` for protected routes), and `src/data/schema.rs` (regenerated by `diesel migration run` — never edit by hand).

### Enum convention

No SQL enums. Enum-like columns are `TEXT` with a `CHECK (col IN (...))` constraint in the migration, plus a Rust enum in the feature's `entities.rs` with `as_str()` and `TryFrom<&str>` (see `UserRole`, `OrganisationStatus`, `AddedBy`, `Cost`, `HereAs`, `Locale`). Usecases validate incoming strings through `TryFrom` before writing.

### RBAC

Roles live in `users.role` (`user` < `moderator` < `admin`), Rust side is `UserRole` with `is_moderator()` / `is_admin()`. The central lookup is `User::fetch_role` (`user/entities.rs`); feature repositories expose it as `fetch_user_role`, and **all role checks happen in usecases** — the auth middleware only authenticates and injects the `Uuid`.

| Action | anonymous | user | moderator | admin |
|---|---|---|---|---|
| Read endpoints (list/search/fetch), signup/signin, visit counter | ✓ | ✓ | ✓ | ✓ |
| Own profile, languages, corridors | — | ✓ | ✓ | ✓ |
| Create organisation (goes to `pending`) | — | ✓ | ✓ | ✓ |
| Update/delete organisation | — | only own (`created_by`) | any | any |
| Upload / set-primary organisation image | — | only own org (`created_by`) | any | any |
| Delete organisation image | — | own upload or own org | any | any |
| Create person / review / saved item / report, vouch, check-in | — | ✓ | ✓ | ✓ |
| Delete review | — | only own | any | any |
| Moderation queue / approve / request-changes / reject | — | — | ✓ | ✓ |
| System reference tables (`POST /common/org_types`, country-connection create/update/delete) | — | — | — | ✓ |

When adding a mutating endpoint: put it in `AUTH_REQUIRED_ROUTES`, then decide in the usecase whether it needs ownership (`ensure_can_manage` pattern) or a role gate (`ensure_admin` pattern in `country_connection/usecases.rs`).

### Domain rules to preserve

- New organisations are created with `status='pending'`; `list`/`search` only ever return `status='live'` rows. Approval flips the flag (see the `moderation` feature).
- Organisation `update`/`delete` are allowed only for `created_by` or a user whose `users.role` is `moderator`/`admin` (checked in `OrganisationUsecase::ensure_can_manage`). When the **creator** (not a moderator) edits a `live` organisation, it goes back to `pending` and a `submitted` event with `editedAfterApproval` is recorded — approved content must never change unreviewed.
- `openNow` is always computed at response time from `opening_hours` (JSONB `{"mon": [["09:00","13:00"]], ...}`) + `timezone` (IANA name) via `compute_open_now` in `organisation/presenters.rs`; it is never stored.
- Geo search (`GET /api/organisation/search`) is PostGIS-free: bbox filtering on the `(latitude, longitude)` index in SQL, Haversine distance + `nearest` sorting in Rust (`haversine_km` in `organisation/repositories.rs`, scan capped at 500 rows).
- Google OAuth: `/oauth/google/login` sets an HttpOnly state cookie that the callback must match (login-CSRF guard); the callback requires `email_verified`, never links to an existing account by email, and redirects to `{FRONTEND_ORIGIN}/auth/google/callback?code=…` (fallback `http://localhost:5173` when `FRONTEND_ORIGIN` is unset) with a single-use 60 s code — the frontend trades it for the session via `POST /api/user/oauth/google/exchange`. Never put the JWT in a URL. The PKCE verifier (5 min) and the login code live in the cache and are consumed atomically with `TypedCache::take` (GETDEL), so OAuth effectively **requires Redis**: with the NoOp cache every callback fails with 401.
- Images: `POST /api/images/upload/{organisation_id}` authorizes the caller (`ImageUsecase::authorize_upload`) **before** reading the multipart body, and the body is capped at 10 MB while streaming; allowed types are jpeg/png/webp/gif.
- Credentials: emails are trimmed+lowercased (`normalize_email`) and looked up with SQL `lower(email)`, backed by the unique index `users_email_lower_key` (case-only duplicates are rejected); passwords are 8 chars to 72 bytes (bcrypt limit, `validate_password`); username 3–50 chars without whitespace; profile free text is length-capped (`validate_max_chars`). There is no email confirmation yet (no mailer).
- Signup v2 creates the user and an optional default corridor in one transaction (`User::signup_v2`). A user has at most one default corridor (partial unique index).
- Controllers must take the authenticated user id from `req.extensions()` (each controller module has its own private `caller_user_id` helper), never from the request body.
- Person status flow: `pending` (moderation) → `awaiting` (approved) → `confirmed`/`claimed` or `declined`. Hidden contacts are gated in ONE place — `PersonContent::from_gated` — and never serialized before confirmed/claimed + the matching privacy toggle. The `/api/person/claim/{token}` endpoints are deliberately public (the token is the credential) and must never be added to `AUTH_REQUIRED_ROUTES` (guard test exists). Because the recommender receives the claim token at creation, `Person::ensure_claimable` only lets a claim be **confirmed** from `awaiting` (never straight from `pending`) and never by the recommender's own account; declining stays possible from `pending`.
- Reviews: exactly one target (DB CHECK `num_nonnulls=1`), unique per author-target (partial unique indexes); create/delete refresh the target's `rating_avg`/`reviews_count` from AVG/COUNT in the same transaction — never patch counters incrementally.
- Moderation: role check in `ModerationUsecase::ensure_moderator`; approve flips org→live / person→awaiting; request-changes requires a note and keeps the item pending. Submit-time auto-checks (duplicate nearby, phone format, creator trust) are written as a `submitted` event into `moderation_events.flags` by the org/person create usecases.
- `saved_items`/`reports` are polymorphic (`kind` + `target_id`, no FK) — clean up in the owning delete usecases when that becomes relevant.
- Community check-in signals (`community` block) are computed on fetch and only attached to the detail payload, never to list/search.

### Dependency injection

`src/utils/di.rs` contains `DiContainer`, which is constructed once at startup in `AppState::new` (`src/app/drivers/middlewares/state.rs`). It holds all usecase instances (each wrapping `Arc<dyn Repository>` + `Arc<dyn Presenter>`), the cache service, and the storage service. `AppState` is shared via `web::Data<AppState>`.

Controllers access dependencies via:
```rust
state: web::Data<AppState>
// then: state.di_container.organisation_usecase
```

### Authentication middleware

`src/app/drivers/middlewares/auth.rs` is a global Actix middleware (`Authentication`) that protects routes defined in the static `AUTH_REQUIRED_ROUTES` array. When a route requires auth, the middleware validates the JWT and inserts the `Uuid` user ID into request extensions. When adding new protected routes, update `AUTH_REQUIRED_ROUTES` in that file.

Route patterns are matched by `path_matches`: a `{param}` segment matches exactly one non-empty path segment (`/api/organisation/update/{id}` matches `/api/organisation/update/<uuid>`), and a pattern ending with `/` is a prefix match (images style). Never rely on plain `starts_with` — a literal `{id}` in the pattern would silently disable auth for that route (this was a real bug). The test `test_every_auth_required_route_matches_a_real_path` guards against regressions; keep it passing when adding routes.

Route-table guard tests (they parse every feature `config.rs` via the test-only `src/app/route_inventory.rs`, so new features are covered automatically):

- `auth.rs` → `test_every_mutating_route_is_protected_or_intentionally_public`: every POST/PUT/DELETE route must be in `AUTH_REQUIRED_ROUTES` or in the test's `INTENTIONALLY_PUBLIC_MUTATING_ROUTES` (each with a reason — adding one is a security decision); `test_intentionally_public_routes_exist_and_are_unprotected` keeps that list honest; `test_every_auth_required_route_protects_a_registered_route` catches typos/renamed routes.
- `main.rs` → `test_every_registered_route_is_in_the_openapi_spec` / `test_every_openapi_operation_is_a_registered_route`: routes and the merged OpenAPI spec must match both ways.

### Rate limiting

`src/app/drivers/middlewares/rate_limit.rs` (actix-governor, keyed by client IP via `ClientIpKeyExtractor`): the whole app gets `api_rate_limit()` (burst 100, 20 req/s), and the credential routes (`/user/signin`, `/user/signup`, `/user/oauth/google/*`) additionally get `auth_rate_limit()` (burst 10, then 1 per 6 s) in `user/config.rs`. Configs are built once in `main` and cloned into workers — never construct a limiter inside the `HttpServer::new` closure, or each worker counts separately.

### Cache abstraction

`src/utils/cache.rs` defines `CacheService` trait and `TypedCache<T>` wrapper. At startup:
- If `REDIS_URL` is set → `RedisCacheService`
- Otherwise → `NoOpCacheService` (silently ignores all cache operations)

Cache keys follow the `CacheKeys` namespace helper in the same file (`org:*`, `cc:*`, `img:*`, `cor:*`, `per:*`, `common:*`); the namespaces must stay disjoint (guarded by `test_feature_patterns_are_distinct`). Repositories invalidate their pattern on every create/update/delete; the `GET /common/*` responses cached by the request-reply middleware (`common:*` prefixes) are invalidated from `CommonRepositoryImpl` on writes. Visit-counter increments drop only the per-id `org:id:*` key to avoid nuking list caches. The `CacheInvalidationMiddleware` (`middlewares/cache.rs`, wrapped around the `organisation`, `country-connection` and `images` scopes) only acts on `DELETE` — repository-side invalidation is what keeps the cache correct. Keys outside `CacheKeys` exist only for OAuth (`oauth:google:pkce:*`, `oauth:google:login-code:*`).

### Storage abstraction

`src/utils/storage.rs` defines `StorageService` trait (object-safe via boxed futures). `src/utils/s3.rs` provides `S3ClientWrapper` (also works with Cloudflare R2). At startup:
- If `S3_ENDPOINT_URL`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_BUCKET` are all set → S3
- Otherwise → `NoOpStorageService` (returns `InternalServerError` on upload/delete)

### Error handling

`src/error.rs` defines `AppError` (Unauthorized, Forbidden, NotFound, UnprocessableEntity, InternalServerError, ServiceUnavailable). It implements `ResponseError` for Actix and `From<_>` for all library error types (Diesel, JWT, bcrypt, Redis, UUID). All controller and usecase functions return `Result<HttpResponse, AppError>`.

- Diesel constraint violations (unique, foreign key, CHECK, NOT NULL) map to **422**, because they are caused by client input, with a generic per-kind message plus the `constraint` name — never Postgres' message/details, which echo column names and values. Every other `DatabaseError` stays a 500 and leaks no DB detail.
- Signin answers the same 401 `Invalid email or password` for an unknown email and a wrong password (with a dummy bcrypt check for timing) — keep it that way.
- `ServiceUnavailable` (503) means a backing integration is not configured — currently the Google OAuth endpoints when the `GOOGLE_*` env vars are absent.

### OpenAPI

The OpenAPI doc is split per feature: **every** feature declares its own `#[derive(OpenApi)] pub struct ApiDoc` in `<feature>/mod.rs` (paths + schemas + tag) and is merged into the root doc in `build_openapi()` in `src/main.rs`. The root `#[openapi(...)]` macro in `main.rs` now only carries `info` + `servers` — do NOT add paths or schemas to it. The API docs UI is **Scalar** (`utoipa-scalar`) at `/scalar`; the raw spec is served at `/api-docs/openapi.json`, and the legacy `/swagger-ui` path 307-redirects to `/scalar`. These stay public because auth is opt-in: only paths listed in `AUTH_REQUIRED_ROUTES` are checked. `SKIP_AUTH_ROUTES` documents the intended-public paths, but `is_skip_auth_route` is currently never called from the middleware — do not rely on it to open a route.

> **RULE** (enforced by the OpenAPI guard tests in `main.rs`): When adding, removing, or updating routes (controllers), you MUST also update the corresponding per-feature `ApiDoc` in `<feature>/mod.rs` — add/remove paths and schemas so Scalar stays accurate, and register a brand-new feature's `ApiDoc` in `build_openapi()`. Do NOT add paths or schemas to the root `#[openapi(...)]` macro in `main.rs`.

## Sub-agents

Repo-specific sub-agents live in `.claude/agents/` and can be invoked via the Agent tool (or `@agent-<name>`):

- **`feature-scaffolder`** — scaffolds a new `src/app/features/<name>/` module and wires all five shared files (features/mod.rs, di.rs, main.rs OpenAPI, AUTH_REQUIRED_ROUTES, migrations). Use for "add a new entity/API area".
- **`db-migrator`** — creates Diesel migrations, verifies `run`/`redo` reversibility on the docker Postgres, checks the regenerated `schema.rs` against Rust struct field order, and rebuilds `scripts/crates`. Use for any schema change.
- **`api-smoke-tester`** — read-only agent that boots the real stack (docker + `cargo run`) and exercises endpoints with curl: auth gates, moderation visibility, ownership/RBAC, image upload to MinIO, `/scalar` docs. Use after a feature lands or to reproduce API bugs.
- **`security-reviewer`** — read-only review of a diff/branch/PR against the invariants from the security audit (#1–#11): `AUTH_REQUIRED_ROUTES` coverage, caller id from JWT only, RBAC before side effects, gated data, DB-error leaks, OAuth/JWT-in-URL, credential rules, rate limiting, uploads, docker secrets. Outputs severity-ranked findings with a concrete attack and fix. Use before merging changes to routes, auth, usecases, migrations or docker files.
- **`usecase-test-writer`** — writes DB-free tests inside `#[cfg(test)]` only, using the stub-repository pattern from `review/usecases.rs`: happy path, each RBAC/status/validation gate with "the rejected call never reached the repository", enum round-trips, presenter leak checks. Never changes production code; a test that exposes a bug is left failing and reported. `corridor/usecases.rs` currently has no tests.

Keep these definitions in sync when conventions change (routes, env vars, RBAC rules).

Repo skills live in `.claude/skills/` (invoked automatically by description or as `/<name>`):

- **`add-endpoint`** — step-by-step checklist for adding/changing/removing a route in an existing feature: DTO → controller + `#[utoipa::path]` + `[authorship]` → usecase validation/RBAC → cache invalidation → `config.rs` → `AUTH_REQUIRED_ROUTES` + count test → rate limit → `ApiDoc` → stub-repo tests → README/AGENTS.md → fmt/clippy/test, ending with a ✓/✗ report. Update it together with this file when a convention changes.
- **`sync-docs`** — brings README/AGENTS/copilot/agent/skill docs and per-feature `ApiDoc`s back in line with the code. Starts with `python3 .claude/skills/sync-docs/check_docs.py` (routes ↔ README, `#[utoipa::path]` ↔ `ApiDoc`, `AUTH_REQUIRED_ROUTES` ↔ real routes + unexpected public mutating routes, env vars, feature list, authorship map; exits 1 on mismatch), then a manual checklist for what the script cannot parse. Fixes docs only and reports code issues separately.

## CI (.github/workflows)

- `rust.yml` — fmt check, build, tests, **plus a separate `scripts-workspace` job** (the scripts crates are not covered by the root build); coverage via tarpaulin → Codecov. All jobs use `Swatinem/rust-cache`.
- `clippy.yml` — `cargo clippy --all-targets --all-features -- -D warnings`.
- `audit.yml` — `cargo audit` for both lockfiles (root + scripts/crates), on dependency changes and weekly. Ignored advisories live in `.cargo/audit.toml`, each with a reason and an exit condition (currently `RUSTSEC-2026-0258`, h2 0.3 via actix-http — unreachable because the server is HTTP/1.x only; drop the ignore if HTTP/2 is ever enabled).
- `dependencies.yml` — weekly `cargo update` PR for both workspaces.
- `release.yml` — builds and attaches the linux binary on `v*` tags.

## Scripts workspace

`scripts/crates` is a **separate Cargo workspace** (`country_parser`, `country_loader`) that depends on the main crate as a library (`landly-server = { path = "../.." }`). It is NOT built by `cargo build`/`cargo test` at the repo root — after changing structs it consumes (notably `Country`/`CreateCountry` in `src/data/models.rs`), verify it still compiles: `cd scripts/crates && cargo build`. The Docker image builds it and `start.sh` runs `country_loader` on first boot when the `countries` table is empty. Seed SQL for manual testing lives in `scripts/data/seed_test_data*.sql`.

## Docker

- The server container healthcheck must target `/api/healthcheck` (there is no `/health` route); `curl` is installed in the runtime image for this. It is a liveness probe only — it does not touch Postgres or Redis.
- The server listens on the hardcoded `constants::BIND` (`0.0.0.0:8080`); `HOST`/`PORT` are exported by `start.sh` and compose but not read by the binary, so leave `PORT` at 8080 (compose maps `${BIND_ADDRESS:-127.0.0.1}:${EXTERNAL_PORT:-8080}` → `${PORT}`).
- `JWT_EXPIRATION` is required by `utils/token.rs` and is passed through docker-compose (default 3600). The old docs mentioned a nonexistent `JWT_EXP_SECS`.
- Service credentials (`POSTGRES_PASSWORD`, `REDIS_PASSWORD`, `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD`, `JWT_SECRET`) are required via `${VAR:?}` — never reintroduce hardcoded defaults. db/redis/minio ports bind to `SERVICES_BIND_ADDRESS` (default `127.0.0.1`), and the bucket is `mc anonymous set download` (read-only; `public` would allow anonymous uploads).
- The redis healthcheck uses an authenticated `PING` as `REDIS_USER` — plain `redis-cli incr ping` always exits 0 even on NOAUTH and mutates a key. Redis auth comes from the ACL file only (`--requirepass` is ignored with `--aclfile`), which must keep `user default off`.
- Shell snippets in compose (`redis` command, `minio-init` entrypoint) read credentials from the container environment as quoted `"$$VAR"` — never interpolate `${VAR}` secrets into shell text. Postgres/Redis passwords must be URL-safe (they are embedded in `DATABASE_URL`/`REDIS_URL`).
- `docker/docker-compose-{postgre,redis,minio}.yml` are standalone single-service files for local experiments (the MinIO one uses the `minioadmin` defaults); the root `docker-compose.yml` is the real stack and the one the rules above apply to.
